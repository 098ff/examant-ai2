# ExamAnt — ข้อกำหนดโครงการจัดตารางสอบด้วย ACO (v3)

> **รายวิชา:** AI2 (2110477)  
> **สมาชิกในกลุ่ม:**  
> 1. 6631305321 Chanatda Konchom (Fai)  
> 2. 6632213421 Sasarose Buranapin (Rose)  
> 3. 6630333721 Sippapas Chavanont (Mai)  
>  
> เอกสารนี้กำหนดตัวโจทย์ ข้อมูล รูปแบบการเรียกอัลกอริทึม และค่าที่ปรับได้ เพื่อให้ทีมพัฒนา backend, frontend และการทดลองใช้สัญญาร่วมกันได้ เป็นฉบับตั้งต้นที่แก้ได้ตามข้อจำกัดจริงของทีม

## 1. ภาพรวมโครงการ

ExamAnt เป็นโครงการทดลองใช้ Ant Colony Optimization (ACO) เพื่อจัดวิชาลงช่วงสอบที่กำหนดไว้ล่วงหน้า โดยใช้ข้อมูลจำลองการลงทะเบียนเรียน

โจทย์มีข้อกำหนดสองระดับ:

- **ข้อจำกัดบังคับ (hard constraints):** (1) นักศึกษาคนเดียวกันห้ามมีวิชาสอบในช่วงเวลาเดียวกัน และ (2) นักศึกษาหนึ่งคนมีสอบได้ไม่เกิน 2 วิชาต่อวัน
- **เป้าหมายปรับปรุง (soft objective):** เมื่อตารางผ่าน hard constraints แล้ว ให้ลดจำนวนกรณี (นักศึกษา, วัน) ที่นักศึกษาคนนั้นต้องสอบทั้งช่วงเช้าและช่วงบ่ายในวันเดียวกัน

ระบบจะเปรียบเทียบ 3 วิธี ได้แก่ Greedy, Random Feasible และ ACO บนชุดข้อมูลและจำนวนช่วงสอบเดียวกัน เพื่อดูคุณภาพตาราง ความสำเร็จในการสร้างตาราง และเวลาในการคำนวณ

### คำถามหลัก

เมื่อใช้ข้อมูลและจำนวนช่วงสอบเดียวกัน ACO สามารถสร้างตารางที่ไม่มีการสอบชน และลดการสอบติดกันได้ดีกว่า Greedy หรือการสุ่มแบบที่สร้างตารางถูกต้องตามข้อจำกัดหรือไม่?

### ขอบเขต

รวม:

- รายวิชา นักศึกษาจำลอง การลงทะเบียน และช่วงสอบ
- การตรวจสอบการสอบชนและจำกัดไม่เกิน 2 วิชาต่อคนต่อวัน
- การนับการสอบในช่วงติดกันภายในวัน
- อัลกอริทึม Greedy, Random Feasible และ ACO
- การทดลองหลายรอบ/หลาย seed และสรุปผลเทียบกัน

ยังไม่รวม:

- การจัดห้องสอบ ความจุห้อง หรือผู้คุมสอบ
- การเลือกวัน/เวลาตามความชอบของนักศึกษา
- การจัดลำดับความสำคัญรายบุคคลหรือข้อยกเว้นเฉพาะคน
- การใช้ข้อมูลนักศึกษาจริง

## 2. นิยามโจทย์และกติกา

ให้มีชุดรายวิชา `C`, ชุดนักศึกษา `S` และชุดช่วงสอบ `T` โดยข้อมูลลงทะเบียนบอกว่านักศึกษาคนใดเรียนวิชาใด อัลกอริทึมกำหนดช่วงสอบหนึ่งช่วงให้แต่ละวิชา

วิชาสองวิชาถือว่า **ขัดแย้งกัน** หากมีนักศึกษาอย่างน้อยหนึ่งคนลงทะเบียนทั้งสองวิชา วิชาที่ขัดแย้งกันต้องอยู่คนละช่วงสอบ และเมื่อจัดแล้วต้องไม่ทำให้จำนวนนักศึกษาคนใดมีสอบเกิน 2 วิชาในวันเดียวกัน

แต่ละวันมีช่วงสอบเพียง **2 ช่วง: เช้าและบ่าย** โดย `slot_index = 1` หมายถึงเช้า และ `slot_index = 2` หมายถึงบ่าย ไม่มีช่วงที่ 3 ทุกวิชาต้องสอบจบภายในหนึ่งช่วง และถูกจัดลงช่วงสอบที่มีอยู่หนึ่งช่วงพอดี หลายวิชาอยู่ในช่วงเดียวกันได้หากไม่มีนักศึกษาร่วมกัน

เมื่อห้ามนักศึกษาสอบสองวิชาพร้อมกัน และมีเพียงสองช่วงต่อวัน นักศึกษาแต่ละคนจึงสอบได้มากที่สุด 2 วิชาต่อวันโดยอัตโนมัติ ข้อจำกัดไม่เกินสองวิชาต่อวันยังเป็นเงื่อนไขของตารางที่ถูกต้อง แต่เป็นผลจากโครงสร้างนี้ ไม่ใช่พารามิเตอร์ที่ต้องปรับแยก

ในโครงการนี้ “สอบติดกัน” หมายถึง **สอบทั้งเช้าและบ่ายในวันเดียวกัน** แม้มีเวลาพักกลางวัน ให้นับเป็น penalty 1 ต่อหนึ่งนักศึกษาต่อหนึ่งวัน หากสอบเฉพาะเช้าหรือเฉพาะบ่ายให้นับ 0 และไม่นับคู่บ่ายวันหนึ่งกับเช้าวันถัดไป

ตัวอย่าง: S001 สอบ Math เช้าและ AI บ่ายวันจันทร์ ตารางนี้ถูกต้องแต่มี penalty 1 สำหรับ S001 ในวันจันทร์ หากย้าย AI ไปเช้าวันอังคารโดยไม่ทำให้ชนกับวิชาอื่น penalty ของคู่นี้จะเป็น 0

ตารางที่จัดไม่ครบ จัดวิชาซ้ำ ใช้ช่วงสอบที่ไม่มีอยู่ หรือมีนักศึกษาสอบชนกัน ถือว่าไม่ใช่คำตอบใช้งานได้

## 3. โครงสร้างข้อมูล (Dataset schema)

เสนอให้ใช้ข้อมูลเชิงสัมพันธ์แบบง่ายสำหรับ MVP จะเก็บเป็น JSON, SQLite หรือฐานข้อมูลอื่นก็ได้ โดยต้องรักษาโครงสร้างและรหัสอ้างอิงให้ตรงกัน

ใน schema นี้ **entity** หมายถึงประเภทข้อมูลหลักแต่ละชนิด ส่วน **record** คือข้อมูลหนึ่งรายการของ entity นั้น เช่น `C01` เป็น record หนึ่งรายการของ Course ข้อมูลแต่ละ entity มีหน้าที่ต่างกัน: ชุดปัญหาหนึ่งชุดรวบรวมข้อมูลทั้งหมด รายวิชาและนักศึกษาคือสิ่งที่โจทย์จัดการ Enrollment เชื่อมว่านักศึกษาลงวิชาใด และ ExamSlot บอกช่วงเวลาที่ใช้จัดสอบ

### 3.1 ExamInstance — ชุดปัญหาหนึ่งชุด

แทนโจทย์จัดตารางสอบหนึ่งกรณี เป็นตัวรวมและระบุชุด Courses, Students, Enrollments และ ExamSlots ที่ใช้ในการทดลอง แต่ละ instance ใช้เปรียบเทียบ algorithms บนข้อมูลชุดเดียวกันได้ เช่น `demo_01`

| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `instance_id` | string | รหัสชุดปัญหา เช่น `demo_01` |
| `name` | string | ชื่อชุดข้อมูล |
| `seed` | integer | seed ที่ใช้สร้างข้อมูลจำลอง |
| `description` | string | คำอธิบายสั้น ๆ |

### 3.2 Course — รายวิชา

แทนวิชาหนึ่งวิชาที่ต้องจัดสอบ อัลกอริทึมจะกำหนด `slot_id` ให้แต่ละ course หนึ่งช่วง และใช้ enrollment ตรวจว่าวิชาใดห้ามสอบพร้อมกัน

| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `course_id` | string | รหัสไม่ซ้ำ เช่น `C01` |
| `course_name` | string | ชื่อแสดงผล |
| `student_count` | integer | จำนวนผู้ลงทะเบียน (คำนวณจาก enrollment ได้ ไม่จำเป็นต้องเก็บซ้ำ) |

### 3.3 Student — นักศึกษาจำลอง

แทนนักศึกษาหนึ่งคนในข้อมูลจำลอง ใช้ตรวจว่าคนเดียวกันมีวิชาสอบชนกันหรือสอบเกินสองวิชาในวันเดียวกันหรือไม่

| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `student_id` | string | รหัสไม่ซ้ำ เช่น `S001` |

ไม่ต้องเก็บชื่อหรือข้อมูลส่วนบุคคล เพราะใช้รหัสจำลองเท่านั้น

### 3.4 Enrollment — ความสัมพันธ์นักศึกษากับรายวิชา

แทนการลงทะเบียนหนึ่งรายการ เชื่อม Student กับ Course โดยนักศึกษาหนึ่งคนลงได้หลายวิชา และวิชาหนึ่งมีนักศึกษาหลายคน Entity นี้เป็นข้อมูลหลักที่ใช้สร้างคู่รายวิชาที่ขัดแย้งกัน

| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `student_id` | string | อ้างถึง `Student.student_id` |
| `course_id` | string | อ้างถึง `Course.course_id` |

คู่ (`student_id`, `course_id`) ต้องไม่ซ้ำกัน

### 3.5 ExamSlot — ช่วงสอบ

แทนช่วงเวลาที่เปิดให้จัดสอบ แต่ละ course จะถูกกำหนดลงหนึ่ง slot ข้อมูลวันและลำดับช่วงภายในวันยังใช้ตรวจข้อจำกัดไม่เกินสองวิชาต่อวัน และคำนวณการสอบติดกัน

| ฟิลด์ | ชนิด | ความหมาย |
|---|---|---|
| `slot_id` | string | รหัสไม่ซ้ำ เช่น `D1_S1` |
| `day_index` | integer | ลำดับวัน เริ่มที่ 1 |
| `slot_index` | integer enum: 1, 2 | 1 = เช้า, 2 = บ่าย เท่านั้น |
| `label` | string | ชื่อแสดงผล เช่น `วันที่ 1 ช่วงเช้า` |

คู่ (`day_index`, `slot_index`) ต้องไม่ซ้ำ แต่ละวันต้องมีสอง records ได้แก่ช่วงเช้าและบ่าย หากมี D วันจะมีทั้งหมด 2D slots ตัวสร้าง dataset ต้องสร้างโครงสร้างนี้เสมอ และ frontend แสดงสองช่วงต่อวัน ห้ามสร้างช่วงที่สามหรือเพิ่ม slot ซ้ำเพื่อแทนห้องสอบ

### 3.6 ข้อมูลที่ส่งเข้าอัลกอริทึม

ส่วนนี้ไม่ใช่ entity เพิ่มเติม แต่เป็นรูปแบบรวมข้อมูลจาก entities ข้างต้นให้เป็น input มาตรฐานที่ algorithm ทั้งสามใช้ร่วมกัน

ไม่จำเป็นต้องให้แต่ละ API อ่านฐานข้อมูลเอง รูปแบบข้อมูลมาตรฐานที่ backend แปลงจากฐานข้อมูลแล้วส่งให้ logic คือ:

```json
{
  "instance_id": "demo_01",
  "courses": ["C01", "C02", "C03"],
  "students": ["S001", "S002"],
  "enrollments": [
    {"student_id": "S001", "course_id": "C01"},
    {"student_id": "S001", "course_id": "C02"},
    {"student_id": "S002", "course_id": "C03"}
  ],
  "slots": [
    {"slot_id": "D1_S1", "day_index": 1, "slot_index": 1, "label": "วันที่ 1 ช่วงเช้า"},
    {"slot_id": "D1_S2", "day_index": 1, "slot_index": 2, "label": "วันที่ 1 ช่วงบ่าย"}
  ]
}
```

ข้อมูลชุดเดียวกันนี้ต้องถูกใช้ร่วมกันทั้งสามวิธีในการทดลองหนึ่งรอบ

## 4. สัญญากลางของอัลกอริทึม/API

ทั้งสาม logic รับ input หลักเหมือนกัน เพื่อให้ frontend เรียกใช้งานและเปรียบเทียบได้ง่าย โดยเปลี่ยนเฉพาะ `algorithm` และ `parameters`

### 4.1 Request มาตรฐาน

```json
{
  "instance_id": "demo_01",
  "algorithm": "aco",
  "parameters": {
    "seed": 42
  }
}
```

`instance_id` ใช้ระบุข้อมูลที่ server โหลดจากฐานข้อมูล ส่วน API ภายในอาจรับ `problem_data` โดยตรงตาม schema ในหัวข้อ 3.6 หากต้องการให้ frontend ส่งข้อมูลเอง

### 4.2 Response มาตรฐาน

```json
{
  "instance_id": "demo_01",
  "algorithm": "aco",
  "status": "success",
  "schedule": [
    {"course_id": "C01", "slot_id": "D1_S1"},
    {"course_id": "C02", "slot_id": "D1_S2"}
  ],
  "metrics": {
    "hard_conflict_count": 0,
    "consecutive_exam_pair_count": 1,
    "penalty_score": 1,
    "runtime_ms": 12.4,
    "attempts": 100,
    "best_iteration": 35
  },
  "parameters_used": {"seed": 42},
  "message": null
}
```

ข้อกำหนด response:

- `status` เป็น `success` เมื่อจัดครบทุกวิชาและ hard conflict เป็นศูนย์; เป็น `no_solution_found` เมื่อค้นหาแล้วไม่พบตารางภายใต้งบที่กำหนด; เป็น `invalid_input` เมื่อข้อมูลไม่ครบหรือผิดรูปแบบ
- `schedule` ต้องมีหนึ่งรายการต่อทุกวิชาเมื่อสำเร็จ
- `hard_conflict_count` นับคู่ (นักศึกษา, คู่รายวิชาที่สอบพร้อมกัน) เช่น สองวิชาที่สอบพร้อมกันมีนักศึกษาร่วม 3 คน ให้นับ 3 กรณี การมีสอบเกินสองวิชาในวันเดียวต้องมีการชนอย่างน้อยหนึ่งคู่ภายใต้โครงสร้างสองช่วง จึงไม่บวกจำนวนที่เกินซ้ำเข้า metric นี้
- `consecutive_exam_pair_count` สำหรับตารางที่ถูกต้อง เท่ากับจำนวนกรณี (นักศึกษา, วัน) ที่มีสอบทั้งเช้าและบ่าย เช่น S001 มีสอบทั้งสองช่วงในวันจันทร์และอังคาร ให้นับ 2; หาก S002 มีสอบทั้งสองช่วงในวันจันทร์ด้วย รวมเป็น 3
- `penalty_score` ใน MVP เท่ากับ `consecutive_exam_pair_count` ยิ่งต่ำยิ่งดี
- `runtime_ms` วัดเวลาของการคำนวณ logic ไม่รวมเวลาโหลดหน้าเว็บหรือวาดกราฟ
- ฟิลด์ที่ไม่เกี่ยวกับ algorithm นั้น เช่น `best_iteration` ของ Greedy ให้เป็น `null` หรือละได้ แต่โครงสร้างหลักควรตรงกัน

### 4.3 การตรวจผลแยกจากตัวสร้างตาราง

ให้มีตัวตรวจกลางที่รับข้อมูลชุดปัญหาและ `schedule` แล้วตรวจว่าจัดครบทุกวิชาครั้งเดียว ใช้ slot ที่มีอยู่จริง และไม่มีการสอบชน พร้อมตรวจจำนวนสอบต่อวันไม่เกิน 2 วิชาเพื่อยืนยันความสอดคล้อง จากนั้นคำนวณ penalty ใหม่โดยอิสระจากโค้ดของทั้งสาม algorithm ผลที่รายงานต้องมาจากตัวตรวจนี้ เพื่อลดโอกาสที่ algorithm ประเมินตารางตัวเองผิด

## 5. พารามิเตอร์ที่ปรับได้

จำนวนช่วงสอบต่อวันคงที่ที่ 2 (เช้า/บ่าย) และไม่เปิดให้ tuning ผ่าน frontend หรือ API จำนวนวันเป็นส่วนของ dataset และต้องใช้เท่ากันในการเปรียบเทียบทุกวิธี

### 5.1 พารามิเตอร์ร่วม

| พารามิเตอร์ | ชนิด/ค่าเริ่มต้น | ใช้กับ | หมายเหตุ |
|---|---|---|---|
| `seed` | integer, default `42` | ทุกวิธี | ทำซ้ำผลได้; Greedy อาจไม่เปลี่ยนผล |
| `max_attempts` | integer, default `400` | Random Feasible | จำนวนครั้งสูงสุดในการสร้างตารางหนึ่งชุด |
| `runs` | integer, default `10` | การทดลองเปรียบเทียบ | จำนวน seed/รอบทดลองต่อวิธี ไม่ใช่จำนวนรอบของ ACO |

### 5.2 พารามิเตอร์ ACO

| พารามิเตอร์ | ชนิด/ค่าเริ่มต้น v1 | ขอบเขตแนะนำ | ความหมาย |
|---|---:|---:|---|
| `num_ants` | 20 | 1–100 | จำนวนมดที่สร้างตารางต่อ iteration |
| `iterations` | 50 | 1–500 | จำนวน iteration |
| `alpha` | 1.0 | 0–5 | น้ำหนัก pheromone |
| `beta` | 2.0 | 0–5 | น้ำหนัก heuristic |
| `rho` | 0.2 | 0.01–0.99 | อัตราการระเหย pheromone |
| `q` | 1.0 | >0 | ค่าคงที่ในการคำนวณ pheromone deposit |
| `initial_pheromone` | 1.0 | >0 | ค่า pheromone เริ่มต้น |

ค่าเริ่มต้นเป็นค่าตั้งต้นสำหรับทดลอง ไม่ใช่ค่าที่รับประกันว่าดีที่สุด Frontend ควรเปิดให้ปรับเฉพาะพารามิเตอร์ที่ผู้ใช้เข้าใจและจำกัดช่วงค่าเพื่อป้องกัน input ที่ผิด

### 5.3 ควบคุมการเปรียบเทียบอย่างเป็นธรรม

- ใช้ dataset และ slot ชุดเดียวกันกับทุก algorithm ในแต่ละ run
- ใช้ชุด seed ที่เหมือนกันหรือบันทึก seed ของแต่ละ run
- Random Feasible และ ACO ต้องมีงบการค้นหาที่รายงานชัดเจน แนะนำให้เปรียบเทียบทั้งจำนวน candidate schedules ที่พยายามสร้างและ runtime
- ACO มีงบโดยประมาณ `num_ants × iterations` ความพยายามสร้างตาราง ส่วน Random มี `max_attempts`; ตั้งค่าเริ่มต้นให้ใกล้กัน เช่น `max_attempts = num_ants × iterations`
- Greedy เป็น deterministic baseline ทำครั้งเดียวต่อ instance และรายงาน runtime แยก
- รายงานผลหลาย run เป็น best, mean และ median ของ penalty ใน run ที่สำเร็จ พร้อม success rate และ runtime; อย่ารายงานเฉพาะ run ที่ดีที่สุดโดยไม่บอกจำนวนครั้ง

## 6. นิยามคะแนนและการจัดอันดับ

ให้ตารางที่ถูกต้องตาม hard constraint มาก่อนเสมอ โดยใช้ลำดับเปรียบเทียบ:

1. ตารางสำเร็จและ `hard_conflict_count = 0` ดีกว่าตารางที่ไม่สำเร็จหรือมี conflict
2. ในกลุ่มตารางที่ถูกต้อง เปรียบเทียบ `penalty_score` โดยค่าน้อยกว่าดีกว่า
3. ถ้าคะแนนเท่ากัน อาจใช้ `runtime_ms` เป็นข้อมูลประกอบ ไม่ใช่ส่วนของ penalty

ห้ามรวม hard conflict กับ penalty เป็นคะแนนเดียวแบบที่อาจทำให้ตารางชนแต่ penalty ต่ำชนะตารางถูกต้อง สำหรับ MVP ใช้การสร้างเฉพาะตัวเลือกที่ไม่ชน หรือปฏิเสธผลที่ไม่ผ่าน validator

## 7. พฤติกรรมที่คาดหวังของแต่ละวิธี

### 7.1 Greedy

1. สร้างกราฟความขัดแย้งจาก enrollment
2. เรียงวิชาจาก degree มากไปน้อย (วิชาที่ชนกับวิชาอื่นมากก่อน); หากเสมอให้เรียง `course_id`
3. สำหรับแต่ละวิชา เลือกช่วงสอบที่ไม่มีวิชาขัดแย้งถูกจัดอยู่แล้วและเมื่อนับรวมแล้วไม่ทำให้นักศึกษาคนใดสอบเกิน 2 วิชาในวันนั้น
4. ในบรรดาช่วงที่ถูกต้อง เลือกช่วงที่ทำให้ penalty เพิ่มน้อยที่สุด
5. หากเสมอ เลือก slot ที่เรียงก่อน
6. ถ้าไม่มี slot ที่ใช้ได้ ให้คืน `no_solution_found`

Greedy เป็น baseline แบบ deterministic เมื่อใช้กติกา tie-break ข้างต้น

### 7.2 Random Feasible

1. สร้างตารางทีละวิชา โดยสุ่มเลือกจากช่วงสอบที่ยังไม่ทำให้เกิด hard constraint violation ทั้งการชนและการเกิน 2 วิชาต่อวัน
2. หากจัดต่อไม่ได้ ให้ถือว่าความพยายามนั้นล้มเหลวและเริ่มใหม่ ภายใต้งบ `max_attempts`
3. เก็บตารางที่สำเร็จและมี penalty ต่ำที่สุด
4. ใช้ `seed` เพื่อให้ทำซ้ำผลเดิมได้

### 7.3 ACO

ACO สร้างตารางหนึ่งชุดต่อมดหนึ่งตัวในแต่ละ iteration โดยจัดวิชาทีละตัวเลือกจากช่วงสอบที่ไม่ทำให้เกิด hard conflict

- **Pheromone `tau`:** ค่าความน่าดึงดูดที่สะสมสำหรับการกำหนดวิชาลงช่วงสอบ
- **Heuristic `eta`:** ความเหมาะสมของการเลือกช่วงนั้น โดย MVP ใช้ค่าที่สูงขึ้นเมื่อการกำหนดนั้นทำให้ penalty เพิ่มน้อยลง
- **ความน่าจะเป็นการเลือก:** แปรผันตาม `tau^alpha * eta^beta` แล้ว normalize เฉพาะช่วงที่ feasible
- **Evaporation `rho`:** ลด pheromone บางส่วนในแต่ละ iteration เพื่อให้ระบบปรับเปลี่ยนการค้นหาได้
- **Deposit:** เพิ่ม pheromone ให้การกำหนดที่อยู่ในตารางคุณภาพดี โดยตาราง penalty ต่ำควรได้ deposit มากกว่า
- เก็บ best-so-far schedule และรายงาน penalty ดีที่สุดที่พบ
- ถ้ามดตัวใดติดทางตัน ให้ถือว่าการสร้างตารางของมดตัวนั้นล้มเหลว ไม่บันทึกเป็นคำตอบ

เพื่อให้การ implement อยู่ในขอบเขต MVP ให้เริ่มด้วย pheromone แบบ `tau[course_id][slot_id]` และกำหนดลำดับจัดวิชาแบบเดียวกับ Greedy (degree มากก่อน) ระบุในรายงานว่าเป็น ACO แบบประยุกต์สำหรับโครงการ ไม่ใช่การอ้างว่าเป็นแบบจำลองเดียวของ ACO ทุกงาน

## 8. API ที่เสนอสำหรับทีม

สามารถใช้ FastAPI โดยแยก endpoint ตามหน้าที่ หรือใช้ endpoint เดียวที่ระบุ algorithm ก็ได้ ข้อเสนอสำหรับเริ่มต้น:

| Method | Path | หน้าที่ |
|---|---|---|
| `GET` | `/instances` | แสดงรายการ dataset ที่มี |
| `GET` | `/instances/{instance_id}` | อ่านรายละเอียด instance |
| `POST` | `/solve` | รัน algorithm หนึ่งวิธีตาม request มาตรฐาน |
| `POST` | `/compare` | รันหลาย algorithm บน instance/seed เดียวกัน แล้วคืนผลรวม |

`/solve` รับ `instance_id`, `algorithm` (`greedy`, `random_feasible`, `aco`) และ `parameters` ที่ตรงกับตารางในหัวข้อ 5

`/compare` รับ `instance_id`, รายชื่อ algorithm, `runs`, seed เริ่มต้น และ parameter ของแต่ละ algorithm ตัวอย่าง:

```json
{
  "instance_id": "demo_01",
  "algorithms": ["greedy", "random_feasible", "aco"],
  "runs": 10,
  "seed_start": 100,
  "parameters": {
    "random_feasible": {"max_attempts": 400},
    "aco": {"num_ants": 20, "iterations": 20, "alpha": 1.0, "beta": 2.0, "rho": 0.2}
  }
}
```

ผล `/compare` ควรมีผลราย run และสถิติรวมแยกตาม algorithm เพื่อให้ frontend ทำกราฟและตารางได้โดยไม่ต้องคำนวณ metric ซ้ำ

## 9. การตรวจสอบ input และกรณีผิดพลาด

ก่อนเริ่ม solve ให้ตรวจว่า:

- `instance_id`, course IDs, student IDs และ slot IDs ไม่ซ้ำภายในชนิดของตน
- enrollment อ้างถึง student และ course ที่มีอยู่จริง
- มีอย่างน้อยหนึ่ง course และหนึ่งวันสอบ แต่ละวันมีสอง slots เท่านั้น (`slot_index` เป็น 1 และ 2 อย่างละหนึ่งรายการ); ค่าอื่น ช่วงที่ขาด หรือคู่วัน/ช่วงซ้ำ ให้คืน `invalid_input`
- จำนวน slots เพียงพอหรือไม่เป็นเรื่องที่อัลกอริทึมตัดสินได้; หากจัดไม่ได้ให้คืนสถานะล้มเหลว ไม่ทำให้ server error
- จำนวนและช่วงค่าพารามิเตอร์อยู่ในขอบเขต
- seed เป็น integer และกำหนดค่าได้

ข้อผิดพลาดควรคืนสถานะและข้อความที่ frontend แสดงได้ เช่น `invalid_input`, `no_solution_found`, `timeout` พร้อมรายละเอียดสั้น ๆ ห้ามส่ง stack trace กลับไปยัง frontend

## 10. เกณฑ์ผลลัพธ์ขั้นต่ำของการทดลอง

สำหรับแต่ละ algorithm ให้เก็บ:

- success rate: สัดส่วน run ที่ได้ตารางครบและไม่มี conflict
- `hard_conflict_count` จาก validator (คำตอบสำเร็จต้องเป็น 0 ภายใต้โครงสร้างเช้า/บ่าย และต้องผ่านการตรวจความครบถ้วนของตารางด้วย)
- `penalty_score` / จำนวนคู่สอบติดกัน
- runtime ต่อ run
- จำนวน attempts หรือจำนวน candidate schedules ที่ลอง
- parameter และ seed ที่ใช้

คำถามในการสรุปผลคือ ACO พบ penalty ต่ำกว่า baseline ได้หรือไม่ ภายใต้งบค้นหาและจำนวนช่วงสอบที่เท่ากันหรือใกล้เคียงกัน และผลนั้นสม่ำเสมอเพียงใด การทดลองใช้ข้อมูลจำลองจึงสรุปได้เฉพาะภายใต้ชุดข้อมูลและสมมติฐานที่ทดสอบ

## 11. สมมติฐานที่ต้องยืนยัน/อาจแก้ในรุ่นถัดไป

- โครงสร้างข้อมูลเริ่มจากจำนวนวิชา นักศึกษา และ slots ขนาดเล็กที่สร้างจำลองเอง
- ทุกวิชามีนักศึกษาลงทะเบียนอย่างน้อยหนึ่งคนหรือไม่ เป็นกติกาที่ทีมสร้างข้อมูลควรกำหนดให้ชัด
- ยืนยันรูปแบบเวลาแล้ว: ทุกวันมีสองช่วงคือเช้าและบ่าย การมีสอบทั้งสองช่วงนับเป็นหนึ่งคู่ติดกัน แม้มีพักกลางวัน
- penalty นับหนึ่งคะแนนต่อ (นักศึกษา, วัน) ที่สอบทั้งเช้าและบ่าย โดยยังไม่ถ่วงน้ำหนักรายคน
- วิธีเลือก heuristic และสูตร deposit ของ ACO เป็นรายละเอียด implement ที่ทีมอาจปรับ โดยต้องบันทึกสูตรสุดท้ายให้ชัดและใช้เหมือนกันตลอดการทดลอง
- จำนวน `runs`, ขนาด dataset และงบ runtime ต้องปรับตามเวลาที่ทีมมีและความเร็วเครื่อง
